# KePosed

简体中文 | [English](README.md) | [AI 协作文档](README_AGENT.md)

## 📖 介绍

**KePosed** 是一个 Android(ARM64)内核级修改框架。

它在**纯内核态**提供跨进程内存读写、系统调用结果塑形与**零注入方法级 hook**(影子页双视图:原字节永不变、零驻留代码)。目标进程内没有常驻代码、没有多余的映射、没有常驻库。**扫不到任何东西,因为那里真的什么都没有。**

名字连接两个血统:`Ke` 是**刻意的双关**——既是 **Kernel 的缩写**(本框架的根本身份:内核级),又是 Windows 内核执行例程族(`KeStackAttachProcess`——附体进程、操纵内存、抽离、不留一物);`Posed` = LSPosed 哲学(方法级 hook、作用域授权)。与 Xposed 家族目标相同、方法不同。**KePosed 不运行 Xposed 模块**——模块是对接版本化内核 UAPI 的原生二进制,不是 Java 桥模块;是哲学血统,不是 API 血统。

用户态 hook 框架(Xposed 系)必须把可执行代码放进目标进程。无论怎么隐藏——抹 magic、伪装 classloader、混淆 maps——载荷*存在于内存中*,而内存可以被扫描。这是一场隐藏方注定落后的拉锯战。KePosed 的解法是不进入这个战场:

| | 用户态 hook 框架 | KePosed |
|---|---|---|
| 载荷位置 | 目标进程内 | 仅内核态 |
| 可检测痕迹 | dex/ELF、classloader、entrypoint hook、匿名可执行页 | **零驻留** ——原字节永不改动(哈希校验照常通过);除你明确修改的数据外分毫未动 |
| 检测成本 | 内存扫描(便宜,且越来越便宜) | 在安卓上,沙箱 app 的检测武库被结构性解除(无内核驱动、pagemap PFN 被屏蔽、无 perf 硬件计数器、无 DMA)——只剩一块带噪的时钟,在 DVFS/热节流抖动与 zram 合法缺页的噪声中读一个微秒级的时序残余 |

> **使用 AI 助手(Copilot / Claude / GPT 等)参与本项目的开发?** 请先阅读 [README_AGENT.md](README_AGENT.md)——它专为 AI 编写,包含本项目**不可协商的设计决策、内核上下文红线与 Native API 分类学**。跳过它直接改代码极可能产出开机循环级缺陷。

## ✨ 功能特性

- **进程内零足迹**
  全部 hook 运行在内核态(一个 KernelPatch Module)。目标进程内没有框架代码、没有模块代码、没有新增映射、没有匿名可执行页。进程内扫描——无论多彻底——一无所获,因为无物可扫。

- **内核只做执行,决策逻辑在用户态(eBPF 哲学)**
  内核侧只暴露窄的、可审计的原语——没有脚本引擎、没有规则解释器、没有业务逻辑。决策逻辑住在非特权用户态模块里。模块崩溃只死自己的进程——永远不伤内核,永远不伤目标。

- **非特权二进制模块 + 能力句柄**
  模块是以**非 root uid** 运行的静态链接二进制——正如 Xposed 模块是无特权的 app。每个特权动作都必须表达为经内核签发句柄(fd)的 KePosed 原语调用;内核逐模块强制执行其注册的能力集(mem_read / mem_write / mem_search / syscall_shape …)。模块 literally 没有任何一条不通守门人的提权路径。

- **Windows 内核分类学的 Native API**
  内核↔模块协议借鉴 Windows 内核例程分类法,按前缀族组织:`Ke`(执行)、`Mm`(内存)、`Ps`(进程)、`Zw`(syscall 塑形)、`Ob`(模块注册)。**不提供 SDK——只有头文件和协议文档。** ABI 是稳定的、带版本的契约(内核签发句柄上的 ioctl);模块可以闭源,因为接口是唯一的接触面。

- **加载器无关**
  `keposed.kpm` 是标准 KernelPatch Module,兼容任何合规加载器——[APatch](https://github.com/bmax121/APatch)(原生 KPM 支持)、[SukiSU-Ultra](https://github.com/SukiSU-Ultra/SukiSU-Ultra)(KPM 桥接)、裸 [KernelPatch](https://github.com/bmax121/KernelPatch)(`sc_kpm_load` / 嵌入 boot 镜像)。加载是加载器的事,不是框架的事;框架永不依赖任何管理器 app。

- **模块之间彼此隔离**
  所有模块刻意共用一个身份(最小权限),隔离因此靠构造而非规则:每个模块出生即进自己的进程命名空间与挂载命名空间"单元格"——兄弟模块在彼此的世界里**根本不存在**(模块之间无法 ptrace、无法偷 fd、无法翻看对方文件;是路径不存在,不是被拦截)。模块登记到内核侧的规则,永远超不过用户安装时授予它的能力与作用域。

- **管理器:一个永不经安装的 APK**
  KePosed 管理器是 APK 形态的 Android 应用,但它**从不经系统安装**——不存在包名记录。由 root 守护进程(keposedd)在需要时拉起——取 LSPosed 免安装管理器之**效果**,但用我们自己的方式:**拉起 ≠ 注入**。管理器作为独立进程运行,从不进入任何他人的进程——零注入身份不动摇。借鉴 LSPosed 的是思路(无形的管理器)与分发/运行时体验;实现是我们自己的路。模块配置页面托管于管理器之内,受框架控制。

- **与 LSPosed 互补——同一目标的不同方法**
  LSPosed 走进程内(生态兼容、模块生态最大);KePosed 走进程外内核态(零足迹、检测免疫)。方法级 hook 两条路都有——他们是驻留式,我们是零注入影子页式。两者可在同一设备并行不冲突。用户态部分以 KernelSU 模块形式分发,模块目录刻意做了命名空间隔离(清单刻意不叫 `module.prop`)——任何 manager 都不会误识别对方的模块。

## 📐 架构

```
┌───────────────────────────────────────────────────────────┐
│  用户态                                                    │
│                                                            │
│  keposedd (root 守护进程)     WebUI      模块二进制        │
│  只管控制面:                 (HTTP)      非特权、          │
│  安装铸柄、事件拉起、                     任意许可证       │
│  联网开关(netns 断网)、                                    │
│  注册表持久化、WebUI 配置                                  │
└──────────────┬─────────────────────────────▲───────────────┘
               │ 控制面:铸柄、递送、拉起     │ 数据面:句柄 ioctl 直达内核
               │ (守护进程只在出生时介入)    │ (守护进程不在环里)
┌──────────────▼─────────────────────────────┴───────────────┐
│  内核态 — keposed.kpm (KernelPatch Module)                 │
│                                                            │
│  Gateway      句柄鉴权、逐模块能力强制                      │
│  Ke 例程      attach / detach、执行层原语                   │
│  Mm 例程      跨进程读 / 写 / 特征码搜索                    │
│  Ps 例程      进程定位、spawn/exit 事件通知                 │
│  Zw 例程      系统调用结果塑形                              │
│  Ob 例程      模块注册表:句柄、能力、撤销                  │
└──────────────┬─────────────────────────────────────────────┘
               │ access_process_vm / hook_syscalln
┌──────────────▼─────────────────────────────────────────────┐
│  目标进程 — 无代码、无库、无映射。                          │
│  只有它的数据在模块决定时才改变。                           │
└─────────────────────────────────────────────────────────────┘
```

**数据面与控制面。** 一切热路径原语——内存读写、特征码搜索、方法 hook、监听规则——由模块**直接向内核**经句柄 ioctl 发起。守护进程从不在数据路径上:零延迟、零负担、零耦合。它只管控制面:安装时铸造并递送句柄、按内核事件拉起模块、逐模块联网开关、注册表持久化。守护进程死亡不影响运行中的模块与句柄——句柄生命周期绑定模块进程,不绑定守护进程。

**模块联网。** 联网是模块的原生能力——**默认开启**:模块直连网络,不经任何中间人。用户可随时关闭。断网是物理性的:模块被**生**在一个空的网络命名空间里(没有网卡、没有路由、没有 DNS)——socket 照常能开,但一个字节也出不去(报错是 `ENETUNREACH`,和一台真没网的机器一模一样——没有"被拦截"的指纹,也没有可绕过的清单)。提前囤好的 socket 在构造上就不可能存在:生来离线的进程根本没网可囤。再打开开关只需按正常网络重新拉起模块。模块登记在内核侧的规则随模块进程退出而撤销(绑定句柄生命周期);重新拉起后,模块自行重新登记。

## 🧩 模块系统(已定设计,未实现)

模块是**压缩包**(格式属实现期决定——设计阶段刻意不固定),内含原生二进制,安装于框架自己的目录之下——嵌套在框架自身的 KSU 模块目录之内,对 KSU 顶层扫描不可见,随框架一起卸载。清单文件刻意**不叫** `module.prop`,KSU/LSPosed manager 永远不会误识别框架模块。清单的具体字段(含能力位)随协议文档定稿——本页不构成任何 API 承诺。

按设计:安装时守护进程向内核注册模块(内核铸造逐模块句柄——一个匿名 fd)。当作用域内的目标进程出现时,守护进程拉起模块二进制:子进程出生即进隔离命名空间(用户关了联网则同时生在空网络命名空间里),随后降到非特权 uid,句柄经 fd 继承递进。每条 gateway 命令在**任何参数解析之前**先校验该模块的能力集;越权返回 `-EACCES`。卸载即撤销句柄并杀进程——凭据即时死亡。

模块可附带可选的配置页面(前端技术构建,参考 KernelSU WebUI 传统)——部分配置逻辑可能闭源,故页面由模块作者编写,托管在 KePosed 管理器内、受框架控制。

## ⚠️ 诚实的能力边界

KePosed **不是**万能的 Xposed 替代品。能与不能,如实陈述:

- ✅ **干净(零痕迹)** —— 系统调用结果塑形(路径隐藏、环境伪装)与数据级内存补丁(数值、字段、属性区)。代码永远不进目标进程。
- ✅ **方法级 hook(v1,零注入形态)** —— 影子页双视图:原页字节永不改动(读/哈希校验恒见原样);调用发生的那一刻,目标线程通过模块自己的内存短暂执行模块回调——映像属于模块进程,对目标任何视角都不可见,永不在目标内驻留。两种平权形态:简单规则(永远返回 X/永远跳过)是模块意志的**数据形态**,复杂回调是同一意志的**代码形态**——驱动对两者同样忠实执行。覆盖 AOT/JIT/native 目标,含热路径(每次调用几微秒);纯解释执行与被内联方法是文档化残余缺口(README_AGENT.md §6.8)。LSPosed 是互补路径——同一目标的不同方法。
- ✅ **作用域覆盖原生可执行文件** —— 作用域条目可以是包名,也可以是直接运行的二进制路径;hook 哪个进程是用户与模块开发者的选择。
- 🛡️ **残余对抗面,如实陈述** —— 时序是任何 OS 上任何 hook 方案都无法完全闭合的唯一信道(页级权限门禁总会留下某种形态的时序差,供统计探针发现)。KePosed 构造性保证的是这条线以上的一切:零驻留代码、零字节改动、无可归因物。目标可以哈希*自己的数据*来发现数据补丁(一切修改类工具皆然——无人免疫);但校验逻辑读取的输入本身可以在 syscall 层被塑形。在安卓上,攻击者仅剩的仪器——自计时——必须先战胜 DVFS 调频抖动、热节流与同量级的 zram 合法缺页,才能提取到一个不可归因的统计比特。硬件级自省(JTAG、hypervisor 级 DMA 扫描)明确不在范围内。
